# Audit de fiabilité — Assistant Caisse

## Avis

Prête pour un **essai supervisé**, pas encore pour l’usage quotidien autonome. Le catalogue en ligne contient 3 fiches marquées réelles, 23 fiches DEMO et 4 procédures DEMO. Les tests valident le respect des données enregistrées, pas l’approbation commerciale de leurs codes. Le microphone physique, Safari/iPadOS, Chrome/Android et le bruit du magasin restent à valider.

## Périmètre et version

Code de départ : `d1cb18bf9187d42fc29a242bc7687ca2a8c2f214`. Interface déployée contrôlée dans le navigateur et défaut « ananas → bananes » reproduit en ligne. Avant cet audit, le serveur ne publiait pas sa version : une correspondance des fichiers statiques ne prouvait pas à elle seule celle du backend. `/healthz` expose maintenant `RENDER_GIT_COMMIT` pour vérifier un déploiement précisément.

Architecture examinée : Flask, SQLAlchemy, PostgreSQL exigé en production, photos téléversées stockées dans PostgreSQL, accès admin partagé et accès caisse distinct. Render déclaré avec un processus Gunicorn et 24 threads. Les plans et factures réels du compte Render n’ont pas été ouverts ni modifiés. Les recherches lisent le catalogue; aucun modèle génératif ne produit de codes ou de procédures. La dictée dépend de SpeechRecognition fourni par le navigateur; son service réel n’a pas été testé.

## Défauts confirmés et corrections

| Conséquence | Reproduction avant correction | Correction |
|---|---|---|
| Mauvais choix de code proposé | Chercher « ananas » : ananas, banane et banane bio apparaissaient. | Priorité au groupe des correspondances littérales avant les ressemblances approximatives. |
| Produit manqué | « code 4011 », « PLU 4060 » ne retrouvaient pas le code existant. | Code exact accepté dans une formulation, sans approximation des chiffres. |
| Produit manqué | « citron jaune » absent malgré la précision déjà inscrite dans la fiche Citron. | Synonyme ajouté à cette seule fiche DEMO et aux données initiales. Aucun code changé. |
| Ancien code encore visible | Laisser une recherche en attente après un premier résultat. | Ancien résultat retiré immédiatement, état « Recherche en cours ». |
| Résultat remplacé par une ancienne réponse | Retarder l’accueil, lancer une recherche, puis libérer l’accueil. | Numéro de requête et annulation couvrant aussi l’accueil et les procédures. |
| Blocage sans reprise | Retenir la réponse réseau au-delà de 12 secondes. | Délai de 12 s, recherche conservée et bouton Réessayer. Ce dépassement est réellement provoqué dans le test DOM. |
| Correction clavier écrasée | Taper une correction puis injecter une ancienne transcription. | Annulation de la dictée et rejet des événements tardifs après arrêt. |
| Micro affiché actif indéfiniment | Simuler un moteur qui ne termine pas après stop. | Arrêt forcé et remise à zéro après 15 secondes. Temps réellement écoulé dans le test. |
| Photo ambiguë | Poivron rouge, oignon jaune et pomme de terre illustrés par plusieurs couleurs/variétés. | Ces trois anciennes illustrations sont masquées dans les résultats caisse; texte « Photo de cette variété à ajouter ». Les fichiers et références en base sont conservés. |
| Inconfort en paysage | Photos affichées avant les noms/codes, codes sous le premier écran à 1024 × 768. | Noms et codes placés avant les photos, écran court compact, contrastes des petits libellés renforcés. |
| Erreur technique sur import | Envoyer un faux XLSX ou une ligne JSON qui n’est pas un objet. | Erreur 400 lisible, aucune modification des données. |
| Limite photo incohérente | Une image valide complétée pour dépasser 5 Mo pouvait passer sous la limite globale de 6 Mo. | Limite de 5 Mo appliquée au fichier côté serveur. |

Risque de concurrence identifié par lecture : l’import verrouillait la révision, contrairement aux modifications individuelles, ce qui permettait un entrelacement indésirable. Tous les changements du catalogue prennent maintenant ce verrou avant d’écrire. Trois modifications simultanées d’une même version donnent un succès et deux conflits 409, sans écraser le gagnant (vérifié sous SQLite; le verrou PostgreSQL reste à éprouver dans une base de recette PostgreSQL).

La sauvegarde utilise désormais une vue cohérente de la base (REPEATABLE READ en PostgreSQL), pour éviter de mélanger des versions de produits et de photos pendant son export. La concurrence exacte export/écritures sous PostgreSQL n’a pas été simulée sur la base de production.

## Résultats mesurés

Les attentes des 166 recherches sont enregistrées dans `tests/fixtures/audit_queries.json` avant les essais. Le catalogue de recette correspond à une copie de la base, avec le seul synonyme corrigé. Il comprend les données DEMO afin de vérifier leur traitement et leur marquage.

| Lot | Avant | Après |
|---|---:|---:|
| 166 recherches : ensemble exact des codes et titres attendu | 159/166 | 166/166 |
| Recherches avec au moins un code inattendu | 3 | 0 |
| Recherches avec au moins un produit attendu manquant | 4 | 0 |
| Même lot dans trois sessions simultanées | 477/498 | 498/498 |
| Scénarios DOM de panne et de dictée simulée | 3/8 | 8/8 |

Le taux final est 166 / 166 = 100 % **sur ce lot**, avec échec dès qu’un code supplémentaire, un code manquant ou un titre de réponse incorrect apparaît. Ce n’est pas un taux de reconnaissance vocale ni une garantie sur un futur catalogue. Dix scénarios attendent plusieurs produits et vérifient l’ensemble des choix, sans imposer arbitrairement un produit unique.

Mesures locales Flask/SQLite, hors réseau : médiane 2,60 ms, 95e percentile 8,61 ms, maximum 22,29 ms; trois sessions : médiane 8,28 ms, 95e percentile 19,13 ms, maximum 65,88 ms. Ces délais ne mesurent ni Render, ni le Wi-Fi du magasin, ni la dictée.

42 tests serveur réussis. Parcours DOM intégrés : connexion, produit créé puis lu depuis une autre vue, modification, ajout de photo, photo trop grande, retrait de photo, annulation et confirmation de retrait, procédures, journal et états vocaux. Les tests destructifs utilisent uniquement des bases locales jetables.

Autres vérifications : droits caisse/admin, absence de session, CSRF, XSS rendu comme texte, images invalides, import CSV/Excel, zéros initiaux des codes, formules Excel refusées, doublons, import atomique, révision périmée, modification concurrente, désactivation, redémarrage sans réensemencement, procédures ambiguës sans réponse arbitraire.

Restauration effectivement exécutée dans une base vide : mêmes produits, procédures et octets des photos après export/restauration. Deuxième restauration refusée sur la base non vide et contenu préservé. Aucun essai de restauration n’a touché la production.

Tests DOM avec réseau simulé : ancien accueil tardif, ancien code masqué, dépassement de 12 s, coupure et reprise avec texte conservé, trois vues distinctes, refus micro/silence/micro absent/service indisponible, correction clavier, dictées successives, arrêt après 15 s, image absente/cassée. Aucune prise de son réelle.

## Interface et services réels

Inspection dans le navigateur Windows : formats 1440 × 900, 768 × 1024, 1024 × 768, 800 × 1280, 1280 × 800 et 390 × 844. Aucun débordement horizontal mesuré sur le résultat contrôlé. Les formats iPad/Android sont des dimensions de navigateur, pas des essais matériels Safari/Chrome Android. Recherche par Entrée vérifiée; clavier virtuel, zoom système et reprise après veille physique restent à tester.

Contrôles HTTP réels : `/healthz` disponible; catalogue, administration et sauvegarde refusés sans session (401); mode production et code caisse obligatoire; CSP et no-store présents. Les quelques requêtes publiques de contrôle ont pris 182 à 248 ms dans ce relevé ponctuel : elles ne constituent pas une mesure représentative des recherches de production.

## Conservation et retour arrière

Une sauvegarde de production a été téléchargée avant correction. Comparaison avant/après de la base : seuls les synonymes du Citron DEMO D008 et sa date de modification ont changé. Produits conservés, codes inchangés, procédures et images identiques. Aucun changement de mot de passe, aucun nouveau service payant ni migration de schéma.

Pour revenir au code précédent : dans Render, choisir un déploiement du commit `d1cb18bf9187d42fc29a242bc7687ca2a8c2f214` (ou déployer spécifiquement ce commit). Vérifier la santé puis connexion, recherche et accès gérant. Le code précédent ne fournit pas de version dans `/healthz`; vérifier aussi les fichiers déployés. Ne pas restaurer la base pour un retour arrière du code. Le synonyme « citron jaune » peut rester, ou être retiré de la fiche dans l’espace gérant. Les trois références photo restent en base : revenir au code précédent les réaffiche.

En cas de restauration de données, utiliser `scripts/restore_backup.py` uniquement sur une **nouvelle base vide**, vérifier produits/photos/procédures, puis préparer la bascule séparément. Ne pas effacer la base actuelle.

## Limites restantes et conditions de passage en magasin

- Faire approuver le vrai catalogue, ses variétés, formats et unités. Le fait que 4011, 4060 et 4083 soient marqués réels ne prouve pas leur adéquation au produit vendu.
- Remplacer ou désactiver les 23 fiches et 4 procédures DEMO avant usage courant. Aucune politique de remboursement, promotion, prix ou paiement réelle n’a été fournie pour validation.
- Ajouter les photos propres aux variétés; une photo générique ne distingue pas à elle seule bio/conventionnel ni le format de vente.
- Effectuer une recette sur les vrais iPad/tablettes Android avec refus puis autorisation micro, plusieurs recherches parlées, silence, bruit, Wi-Fi lent, coupure, clavier virtuel et veille/reprise. Aucun taux de dictée réelle n’est revendiqué.
- Vérifier les écritures/imports concurrents et la sauvegarde sur PostgreSQL de recette, ainsi que le débit sur un catalogue de taille réelle. Le lot actuel contient 26 produits, pas 10 000.
- Le service n’offre pas de catalogue hors ligne : il masque les résultats lors d’une coupure détectée. La page hors ligne sert seulement à expliquer l’indisponibilité.
- La configuration de sauvegarde automatique, la facturation et la conservation Render n’ont pas été vérifiées dans le tableau de bord. L’export manuel et la restauration locale, eux, ont été testés.

Conclusion : version adaptée à un **essai supervisé** avec ces limites explicites. Une utilisation quotidienne autonome serait prématurée tant que les données approuvées et les essais physiques ne sont pas complétés.
